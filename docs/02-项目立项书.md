# 02 项目立项书（评审稿）

## 1. 项目定义

- 项目名称：AI 运营提效平台。
- 当前阶段：Gate 0，需求分析与立项评审。
- 项目负责人：何鹏云（简历口径，待组织确认）。
- 候选团队：算法、后端、产品、测试、数据及运维；“12 人”需按实际确认。
- 服务对象：培训运营、门店/区域运营、店长、技师/服务顾问及车主。

## 2. 立项目标

复用智能客服已验证的模型服务、RAG、Agent 编排、Java 集成、评测和灰度能力，以统一平台承载四类运营 AI 场景。先通过场景级 POC 证明可用性和业务价值，再按风险由低到高分批试点，避免把“平台建设”变成没有业务结果的技术工程。

## 3. 价值假设

| 方向 | 假设 | 验证方式 |
|---|---|---|
| 运营效率 | 降低课件制作、质检和方案生成中的重复人工 | 人工工时、周期、单位产出前后对比 |
| 服务质量 | 提升检查覆盖、一致性和建议标准化 | 覆盖率、采纳率、质量抽检和投诉护栏 |
| 经营辅助 | 缩短报价/方案响应并辅助转化 | 对照试点的耗时、采纳与转化漏斗 |
| 管理能力 | 过程和效果可量化、可追溯、可回滚 | 版本、证据、审核、埋点与审计完整率 |
| 技术资产 | 形成可复用 AI 接入与交付基座 | 新场景接入周期、组件复用率和变更成本 |

上述均为待验证假设，不是收益承诺。

## 4. 分阶段交付物

### Gate 0：需求与立项

- 四场景现状流程、痛点证据、基线和优先级评分。
- 数据/接口/合规盘点；价值测算与指标口径。
- POC 主场景、范围、资源、风险和验收方案。

### Gate 1：POC

- 统一 FastAPI + LangGraph 集成骨架及业务接口 stub。
- 主场景真实脱敏样本的端到端演示。
- 模型/规则/人工基线评测、风险与工程化差距报告。
- Gate 1 是否进入生产试点的决策报告。

### Gate 2：单场景试点

- 生产级接口、权限、监控、审核、降级、灰度和回滚。
- 单店或约 1% 流量试点结果及业务归因报告。

### Gate 3：扩场景/扩量

- 达标场景规模化方案；下一场景接入。
- 运营后台、版本治理、SLA、培训、运维和复盘材料。

## 5. 首期范围基线

### In Scope

- 四场景需求与数据调研、优先级评估。
- 1 个主场景 POC；智能客服共性基座适配。
- 门店/技师等必要接口契约与 stub。
- 真实样本评测、人工审核、埋点、降级与安全验证。

### Out of Scope

- 四场景同时生产化或全国上线。
- 自动发布、自动处罚、自动改价等高风险无人审核动作。
- 业务主系统重构、基础模型训练和 GPU 平台重建。
- 未经基线验证的固定收益与上线承诺。

### 待评审争议项

- 首个 POC 选择哪个场景。
- POC 是验证统一基座还是承诺完整平台化。
- 报价与养护方案是否同时进入首轮生产试点。
- 多模态模型由算法团队交付还是纳入本项目研发范围。

## 6. 方案原则

1. 业务结果优先于模型炫技，四场景分别建立价值闭环。
2. 共性能力平台化，场景数据、策略和风险边界隔离。
3. 生成内容必须有证据、版本和必要的人工审核。
4. 模型不直接控制价格、处罚或安全维修决策。
5. 先真实样本 + stub，再单店/1% 灰度，达标后扩量。
6. 算法模型与业务系统通过稳定契约解耦，任一模型可替换和回滚。

## 7. RACI 草案

| 工作项 | 项目负责人 | 业务/产品 | 算法 | 后端 | 数据 | 测试/运维 |
|---|---|---|---|---|---|---|
| 目标、范围和优先级 | A/R | R | C | C | C | C |
| 业务基线与验收口径 | A | R | C | C | R | C |
| 模型/多模态能力 | A | C | R | C | C | C |
| AI 服务与接口骨架 | A/R | C | C | R | C | C |
| 业务系统集成 | A | C | C | R | C | C |
| 效果与安全验收 | A | R | C | C | C | R |
| 灰度、发布和回滚 | A | C | C | R | C | R |

A=最终负责，R=执行负责，C=协作；必须具体到人后再冻结排期。

## 8. 里程碑与退出决策

| 里程碑 | 完成标准 | 决策 |
|---|---|---|
| M0 需求/数据盘点 | 基线、优先级、数据、接口、合规、范围签字 | 是否进入 POC |
| M1 主场景 POC | 真实样本闭环与评测达门槛 | 是否生产试点 |
| M2 单店/1% 灰度 | 业务指标与护栏达标 | 扩量、调整或停止 |
| M3 单场景规模化 | 稳定性、收益、组织承接达标 | 是否接入下一场景 |
| M4 平台化交付 | 四场景按各自 Gate 达标，SLA/运维完成 | 转运营与复盘 |

不预设虚假日期；确认数据、接口 owner 和发布窗口后倒排。

## 9. 主要风险

| 风险 | 早期信号 | 应对 |
|---|---|---|
| 四场景范围过大 | 所有链路同时要求上线 | 强制场景评分和独立 Gate，首期只做 1 个 POC |
| 数据/标注不足 | 样本口径不一、标签争议 | 数据准入、双人复核、黄金集和分层评测 |
| 离线好但业务无收益 | 精度提升、流程耗时/转化不变 | 真实流程对照与埋点，联合业务验收 |
| 幻觉/错价/安全错误 | 无证据生成或越权调用 | RAG/规则护栏、工具白名单、人工确认、停止线 |
| 图像质检误报伤害门店 | 申诉率或区域偏差高 | 置信度分级、人工复核、分店型评测 |
| 业务不采用 | 人工修改率高 | 共创流程、收集原因、嵌入原作业系统 |
| 基座升级影响多场景 | 模型变更后指标波动 | 契约测试、黄金集回归、灰度和版本冻结 |
| 收益归因不清 | 多项运营策略同期变化 | 对照组/影子运行、统一口径和业务签字 |

## 10. Gate 0 准入条件

- sponsor、四场景业务 owner、技术 owner 明确。
- 每个场景现状、痛点和基线有证据。
- 完成价值/可行性/风险/数据就绪度评分并选定主 POC。
- 指标、目标、护栏、停止线及口径 owner 明确。
- 数据合法可用，接口 owner 和系统边界确认。
- In/Out 范围、资源、环境、预算和发布窗口签字。
- 人工审核、降级、回滚及事故责任人明确。

## 11. 当前建议

**Conditional Go：批准四场景需求深化和一个主场景的真实样本 POC；暂不批准四场景同时工程化或全量建设。**

原因：简历表明共性 AI 基座和交付路径已有实践基础，但当前缺少四场景的业务基线、优先级、具体效果门槛、合规结论和团队数字，尚不能承诺规模化价值与排期。
