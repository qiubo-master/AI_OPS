# AI检测报价项目立项需求（V0.1）

## 1. 项目定义

AI检测报价是面向门店技师、服务顾问、店长和运营人员的经营辅助系统。系统接收车辆档案、检测结果、故障码、技师结论及图片证据，识别需要处理的异常项，查询实时商品、服务、库存、价格和活动规则，生成可解释、可编辑的报价草案，经门店人员确认后提交现有交易系统。

本项目中的AI只负责理解、归纳、推荐和解释；最终价格、库存、促销、税费和订单状态必须以业务系统实时返回为准。未经人工确认，AI不得自动改价、下单或向客户承诺服务结果。

## 2. 立项背景

### 2.1 当前问题

- 检测结果、车辆信息、商品、工时、库存和价格分散在多个系统中。
- 服务顾问需要依赖个人经验把检测异常转换为服务项目和商品组合。
- 同类检测结果在不同门店可能形成不同报价口径。
- 人工查价、找货、核对适配关系和组织客户解释耗时较长。
- 报价被拒、改价、退单和投诉原因缺少结构化回流。
- 图片检测、故障码、检测报告与报价之间缺少统一证据链。

### 2.2 建设机会

项目可复用现有DeepSeek-R1、全业务RAG、共享视觉能力、车辆档案、商品与交易接口，通过工具调用和规则护栏形成“AI辅助＋确定性业务系统”的报价闭环。

## 3. 项目目标

### 3.1 业务目标

- 缩短从检测完成到形成报价草案的时间。
- 提高检测异常项到服务项目的映射完整性和一致性。
- 降低人工查找商品、库存和价格的操作成本。
- 为客户提供有检测证据、有业务依据的报价解释。
- 建立报价采纳、修改、转化、退改和投诉的数据闭环。

### 3.2 技术目标

- 建立检测结果标准化和异常项语义模型。
- 建立车辆适配、服务项目、商品、工时、价格和库存的统一工具调用层。
- 使用规则引擎承担安全规则、互斥关系、必选项和价格计算。
- 使用DeepSeek-R1生成报价摘要和客户解释，不让大模型直接生成权威价格。
- 全链路记录输入、工具返回、规则版本、模型版本和人工修改。

### 3.3 非目标

- 不替代检测设备或技师专业判断。
- 不由大模型直接生成商品价格、库存和优惠金额。
- 不自动改价、自动下单或自动发送客户承诺。
- 不重建商品中心、库存中心、价格中心、订单中心和支付系统。
- 不在缺少车辆适配验证时推荐具体商品。
- 不以提升客单价为唯一目标，不允许过度维修推荐。

## 4. 目标用户

| 用户 | 核心任务 | 主要价值 |
|---|---|---|
| 门店技师 | 提交检测结果、确认异常和施工必要性 | 减少重复录入，保留专业判断 |
| 服务顾问 | 生成、调整、解释报价并与客户确认 | 缩短报价时间，统一解释口径 |
| 门店店长 | 审核高金额、特殊折扣和风险报价 | 降低错价与投诉风险 |
| 区域运营 | 查看门店报价效率、采纳和异常 | 发现流程和商品供给问题 |
| 商品/价格运营 | 维护适配、价格和活动规则 | 保持交易主数据权威 |
| 客服 | 基于已确认报价回答客户问题 | 减少信息不一致 |

## 5. 首期范围

### 5.1 输入

- VIN、车牌关联车辆、品牌车型、年款、配置和里程。
- 检测设备结构化结果。
- 技师手工检测项和结论。
- 故障码、胎压、花纹深度、电瓶、制动等检测数据。
- 检测照片、报告图片及共享视觉服务的结构化结果。
- 历史维修保养订单和近期已更换项目。

### 5.2 输出

- 检测异常项清单及证据。
- 建议服务项目、推荐原因和风险等级。
- 适配商品候选、门店/区域库存和替代品。
- 工时、商品、优惠、税费和应付金额明细。
- 必做、建议、观察三个优先级。
- 面向服务顾问和客户的两套解释。
- 待确认项、冲突项和不确定项。

### 5.3 P0场景

1. 轮胎检测结果生成轮胎更换/修补/观察建议和报价草案。
2. 电瓶检测结果生成检查、更换或观察建议。
3. 常规保养检测中明确异常项的报价草案。
4. 检测报告图片通过OCR/视觉服务结构化后辅助报价。

制动、转向、发动机等高安全风险项目首期可展示建议，但必须由技师确认，不能仅凭模型结果形成直接施工报价。

## 6. 核心流程

```text
车辆与检测数据进入
→ 数据完整性与质量校验
→ 异常项标准化
→ 规则与RAG检索
→ 查询适配商品/服务/库存/实时价格
→ 规则引擎组合报价
→ AI生成解释和待确认项
→ 技师/服务顾问修改确认
→ 高风险/高金额审批
→ 提交交易系统
→ 回收采纳、成交、退改和投诉结果
```

## 7. 价值与指标

### 7.1 业务指标

- 报价草案生成时长。
- 服务顾问完成报价总时长。
- 报价草案采纳率和修改率。
- 报价到订单转化率，仅作为观察指标，需控制促销等干扰变量。
- 客户解释使用率。

### 7.2 质量指标

- 异常项识别完整率。
- 服务项目映射准确率。
- 车辆适配通过率。
- 价格与交易系统一致率。
- 报价解释引用正确率。

### 7.3 强护栏

- 权威价格错误数为0。
- 不适配商品进入确认报价数为0。
- 高风险项目未经人工确认进入订单数为0。
- 过度推荐率、退改率、投诉率不高于对照组。
- 依赖系统不可用时不得使用缓存旧价格对客户承诺。

## 8. POC设计

- 试点范围：建议5至10家门店。
- 试点场景：轮胎、电瓶、常规保养三个低到中风险场景。
- 运行方式：前2周影子模式，与人工报价并行，不影响真实订单。
- 样本规模：每场景至少500至1000条脱敏历史样本，按车型、门店和时间切分。
- 对照方式：比较人工报价耗时、完整率、修改原因和交易一致性。

## 9. 依赖条件

- 车辆档案/VIN解析接口。
- 检测结果或检测设备接口。
- 服务项目与商品适配接口。
- 门店库存、区域库存接口。
- 实时价格、促销和会员权益接口。
- 工时、税费和订单试算接口。
- 交易系统创建草稿/确认订单接口。
- 共享视觉服务、RAG和DeepSeek-R1接口。

任一权威接口缺失时，只能做离线POC或使用Stub，不得进入真实交易试点。

## 10. 资源与费用初估

| 类别 | 初步估算 |
|---|---:|
| 数据治理与历史样本整理 | 3万至8万元 |
| 商品/价格/库存/交易接口改造 | 8万至20万元 |
| AI编排、规则与报价服务研发 | 20万至45万元 |
| 前端、测试、审计与监控 | 10万至25万元 |
| POC总投入 | 41万至98万元 |

费用为内部立项估算，主要不确定性来自存量系统接口完整度和车辆适配数据质量。

## 11. 风险与控制

| 风险 | 控制措施 |
|---|---|
| 大模型编造价格或库存 | 价格和库存只允许工具调用返回；响应Schema校验 |
| 车辆适配错误 | 适配服务为硬校验，不通过不得进入确认报价 |
| 过度维修推荐 | 必做/建议/观察分级；规则阈值；人工确认；投诉回流 |
| 检测数据不完整 | 明确缺失字段并阻断高风险建议 |
| 活动价格变化 | 报价确认前重新试算；设置有效期 |
| 服务顾问盲目采纳 | 展示证据和依据；高风险强制确认 |
| 业务转化评价失真 | 使用对照组，拆分促销、门店和人员差异 |

## 12. 里程碑

| 阶段 | 周期 | 交付 |
|---|---:|---|
| Gate 0 数据与接口审计 | 2至3周 | 主数据映射、接口清单、风险分级 |
| 离线报价POC | 4至6周 | 历史样本评测、规则和解释原型 |
| 影子模式 | 3至4周 | 与人工报价并行、差异分析 |
| 5至10店灰度 | 4至6周 | 人工确认的真实草稿与指标 |
| Gate 2规模化评审 | 2周 | 价值、质量、护栏和成本报告 |

## 13. Gate 0待确认

1. 首期检测设备和数据来源。
2. 商品适配、库存、价格和订单试算接口负责人。
3. 报价有效期、价格刷新和锁价规则。
4. 高风险/高金额审批阈值。
5. P0服务品类和试点门店。
6. 人工报价基线、错价和退改单基线。

## 14. 立项建议

建议Conditional Go：批准接口审计、离线POC和影子模式；只有实时价格、库存、车辆适配、人工确认、审计和降级全部可用后，才允许进入真实报价草稿试点。
